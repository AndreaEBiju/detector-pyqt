# M1 signal-viewer spike — results

## Purpose

Validate that pyqtgraph + h5py lazy loading can deliver responsive
pan / zoom on a 2-hour multi-channel recording, before committing to
the M2+ migration build.

## How to reproduce

```bash
cd /Volumes/PortableSSD/detector-pyqt
pip install -e ".[dev]"   # once
python scripts/m1_benchmark.py --recording <path/to/2h.mat>
```

The benchmark times 20 random pans at three viewport sizes per the
plan's M1.3 targets and writes the AUTO section below. Run multiple
times against different recordings; results from each run replace
the AUTO block (prose around it is preserved).

For interactive feel — what the benchmark can't measure — drive the
GUI directly:

```bash
python ui/app.py <path/to/2h.mat>
```

Scroll-wheel zoom, drag-pan, pinch on macOS — see whether it feels
responsive in the seat, not just on paper.

## Pass bars (plan M1.3)

| Viewport | Target | Rationale |
|---|---|---|
| 60s   | < 100 ms  | perceptually instant, single pan keystroke |
| 600s  | < 300 ms  | still feels fast for medium-zoom navigation |
| 7200s | < 1000 ms | entire recording — slowest but still usable |

Peak RSS target: **< 2 GB** for a 2h recording (8.6 GB raw float32 →
lazy loading keeps memory bounded).

## Preliminary results — local 22-min recording (no Qt, read-only)

Before the full Qt benchmark on the 2-hour Drive recording, we tested
just the `LazyRecording.get_range()` read path on the local 22-min
file `M10E10_ORE_CME_stim_rec_1908_notched.mat`. Two scenarios:

**Scenario A — raw MATLAB `_notched.mat` `(n_ch, N)` layout (the
existing on-disk format):**

| Viewport | mean read (ms) | target (ms) | verdict |
|---------:|---------------:|------------:|:--------|
|     60s  |   ~700         |   100       | ❌ fail |
|    600s  |  ~4 800        |   300       | ❌ fail |
|   1200s  | ~11 400        |   —         | unusable |

Cause: `(n_ch, N)` row-major HDF5 means each 60s viewport read is 5
non-contiguous slices, one per channel. Disk seeks dominate.

**Scenario B — after one-time ingest to flat `(N, n_ch)` HDF5 with
chunked storage along time (`scripts/m1_ingest.py`):**

| Viewport | mean read (ms) | target (ms) | verdict |
|---------:|---------------:|------------:|:--------|
|     60s  |   ~96          |   100       | ✅ pass (just) |
|    600s  |   ~800         |   300       | ❌ fail |
|   1200s  |  ~1 800        |   —         | (extrapolates to ~7000ms for 7200s) |

The 28× speedup at 60s closes the small-viewport gap but the wide-
viewport reads are still bound by raw bandwidth — 14M samples take
~800ms to read from disk regardless of layout. That confirms the
plan's M1.4 mitigation is needed for wide-zoom scenarios:
**pre-computed downsampled overview file** for viewports beyond ~2 min.

Ingest cost on this hardware: 22-min file → 26s conversion, output
505 MB. Extrapolates linearly to ~150s for a 2-hour file.

## Decision

After running the benchmarks AND driving the GUI:

- [ ] Proceed to M2 (browser + labeling)
- [ ] Conditional: proceed with mitigation X
- [ ] Abort migration; document why

### If proceeding

What carries forward into M2:
- `ui/widgets/signal_viewer.py` (LazyRecording + MultiChannelViewer)
- `ui/app.py` toolbar + reset/fit actions
- `scripts/m1_benchmark.py` becomes the perf-regression test we
  re-run after every signal-viewer change

### Mitigation options if numbers don't clear the bars (plan M1.4)

1. **Pre-compute downsampled overview** at ingest time — separate
   smaller file used for wide-zoom viewports.
2. **PyQtGraph OpenGL backend** — `pg.setConfigOptions(useOpenGL=True)`
   for hardware-accelerated paths.
3. **Abort and revisit later** when data size grows materially.
